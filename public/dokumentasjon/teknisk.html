    1 Kort for alle

    Hva er det?

    ht14.no er sameiets egen nettside med startsiden, denne dokumentasjonen og Badehusappen – en nettside som oppfører seg som en app. Der ser vi når badehuset er ledig, booker, avbestiller og sjekker inn. Den virker på mobil, nettbrett og PC, og kan legges på Hjem-skjermen.

    I dag sender vi en e-post til en nabo som har oversikten. Det har fungert fint takket være ham, men det blir mye e-post, og alt hviler på én person. Med Badehusappen ser alle den samme kalenderen og booker selv.

    Dagen er delt i tre perioder: formiddag 10–14, ettermiddag 14–17 og kveld 17–24. Reglene står i Regler for bruk av badehuset.

    Hvem kan gjøre hva

    Hvert hus (A, B, C og D) får én felles innlogging. Med den kan dere se kalenderen, booke, avbestille, sjekke inn, bekrefte bruk og se historikk og statistikk. En administrator kan i tillegg bytte passord for et hus, logge ut en mistet mobil, legge inn regelendringer, gjøre unntak og rette feil. Alt administratorene gjør, logges.

    Trygghet og personvern

    • Ingen registrerer seg selv – administratoren gir hvert hus e-post og passord. Mobilen kan huske passordet, og dere holder dere innlogget i omtrent ett år.
    • Bookingene lagres i en database hos Cloudflare, aldri på de offentlige sidene. Passord lagres aldri i klartekst.
    • Hver natt tas det en kopi til et privat lager. Ingen bookinger slettes, og alle endringer kan spores.
    • Ikke med i starten: varsler på e-post/SMS og Face ID uten passord (passkeys). Det kan komme senere.

    2 Overordnet (HLD)

    Hvilke deler løsningen består av, og hvorfor. Alt kjører på gratisplanene hos Cloudflare og GitHub, så det koster 0 kr i drift.

    Komponenter

    DelHva den gjør
    ht14.noSameiets adresse. Kjøpt hos Domeneshop, DNS hos Cloudflare.
    Cloudflare Worker «ht14» med statiske filerServerer startsiden (/), dokumentasjonen (/dokumentasjon/) og Badehusappen (/badehusappen/). Senere også innlogging og booking på /api/.
    Cloudflare D1 «ht14»Databasen: hus, innlogginger, bookinger, økter, feilede innlogginger og en hendelseslogg.
    Nattlig kopi (Cron Trigger)Hver natt skriver Workeren bookinger og brukere som CSV og JSON til det private repoet FluxReveal/ht14-data – aldri passord-hasher. Git gir full historikk, og CSV-filene åpnes i Excel.
    GitHubFluxReveal/ht14 (offentlig: sidene og koden, ingen hemmeligheter) og FluxReveal/ht14-data (privat: nattlig kopi).
    Workers BuildsPubliserer automatisk når main endres. Andre grener får en egen forhåndsvisningslenke.

    Fire hus som booker badehuset, kommer aldri i nærheten av grensene på gratisplanene.

    Dataflyt

    Status («pågår», «ferdig») regnes ut fra klokka i norsk tid når noe vises. Hver periode lagres som en egen booking; en heldag er tre bookinger med felles group_id.

    Innlogging og økter

    Én innlogging per hus (A–D) med e-post og passord, sjekket i Workeren. Passord lagres bare som PBKDF2-hash med salt og en hemmelig «pepper». Antall runder justeres slik at en innlogging holder seg innenfor gratisplanens 10 ms CPU per forespørsel. Skjemaet bruker riktige autocomplete-verdier, så iPhone og Android kan lagre passordet.

    Etter innlogging får mobilen cookien __Host-ht14_okt (HttpOnly, Secure, SameSite=Lax) som varer i ca. ett år. Øktene og telleren for feil passord ligger i D1. Sidene og API-et ligger på samme adresse, så cookien er en vanlig førsteparts-cookie som også Safari på iPhone godtar.

    Sikkerhet

    • Hemmeligheter: SESSION_PEPPER og GH_DATA_TOKEN ligger bare som Worker-secrets – aldri i koden. Derfor kan repoet ht14 være offentlig.
    • Token: GH_DATA_TOKEN er et fine-grained GitHub-token som bare kan skrive til ht14-data.
    • Regler: sjekkes alltid i Workeren, så det hjelper ikke å fikle med JavaScript i nettleseren.
    • Andre nettsider: Workeren godtar bare endringer fra ht14.no (Origin-sjekk), sender ingen CORS-headere og krever gyldig økt.
    • Dobbeltbooking: hindres i databasen – samme dato og periode kan bare ha én aktiv booking.
    • Sporbarhet: hendelsesloggen i D1 viser hvem, når, fra, til og kommentar, og Git-historikken i ht14-data viser alle tidligere versjoner.

    Tekniske valg

    Én leverandør for adresse, sider, innlogging og database gjør det enkelt å drifte. Med alt på ht14.no ligger sidene og API-et på samme sted, så innloggingen virker på iPhone. D1 er en ekte database, så to hus kan ikke booke samme periode samtidig. Den nattlige kopien i GitHub gjør oss uavhengige: dataene kan alltid tas med videre. Cloudflare Access ble valgt bort fordi den gir maks 30 dagers innlogging med engangskoder på e-post.

    3 Detaljert (LLD)

    For den som skal bygge, drifte eller videreutvikle. Navn på filer, felt og endepunkter kan justeres underveis.

    Utkastet nå: Badehusappen har ingen innlogging, og store.js lagrer bookingene i nettleseren (localStorage). store.js har de samme funksjonene som API-et skal ha, så når innlogging og booking kommer, byttes bare den fila ut.

    Datamodell

    Utkast i schema.sql. Det legges inn i D1 først når sameiet har godkjent reglene.

    TabellInnhold
    housesA–D med navn og farge
    usersÉn innlogging per hus, pluss administratorer: e-post, rolle, passord-hash
    bookingsDato, periode (AM 10–14, MID 14–17, PM 17–24), hus, status, group_id
    sessionsInnloggede mobiler (bare hash av cookien lagres)
    login_attemptsFeil passord, for en kort pause etter flere forsøk
    eventsHendelseslogg: hvem, når, hva, fra, til, kommentar

    Utdrag av rules.json – alle regler ligger her, så de kan endres uten kodeendring:

    { "timezone": "Europe/Oslo",
  "periods": { "AM":  { "label": "Formiddag",   "start": "10:00", "end": "14:00" },
               "MID": { "label": "Ettermiddag", "start": "14:00", "end": "17:00" },
               "PM":  { "label": "Kveld",       "start": "17:00", "end": "24:00" } },
  "bookingWindow": { "months": 3 },
  "summer": { "months": [6, 7, 8], "maxPerWeekdayPerMonth": { "fri": 1, "sat": 1, "sun": 1 },
              "maxDaysPerWeekend": 1 },
  "liftSummerRulesWhenDaysBefore": 7, "lateCancellationDays": 7 }

    Regelmotor

    rules-engine.js er rene funksjoner, så samme kode kjører i nettleseren (rask tilbakemelding) og i Workeren (som bestemmer).

    • validateBooking sjekker én periode: gyldig input → ikke passert → ikke startet → innenfor 3 måneder → ledig → (admin-unntak) → under 7 dager? da OK → sommer og fre/lør/søn? → kvote per ukedag → én dag per helg.
    • validateBookingMulti tar flere perioder: heldag avvises etter kl. 10, og alt eller ingenting lagres.
    • Kvoten teller dager, ikke perioder. Testene ligger i tools/tests/ og kjøres med node --test tools/tests/.

    Statuser

    CANCELLED og CANCELLED_LATE frigjør perioden. CANCELLED_LATE teller fortsatt i sommerkvoten. I statistikken teller CHECKED_IN og COMPLETED som bruk.

    API

    Alle kall går til /api/ på ht14.no, med JSON og økt-cookie (unntatt innlogging). I dag finnes bare /api/helse.

    EndepunktHva
    GET /api/helseSvarer {"ok":true} – virker nå
    POST /api/login, /logout, /password, GET /api/meInnlogging, utlogging, bytte passord, hvem er jeg
    GET /api/calendar, /history, /stats, /rulesKalender, historikk, statistikk, regler
    POST /api/bookings {date, periods}Book én eller flere perioder
    POST /api/bookings/{id}/cancel | checkin | confirmAvbestill, sjekk inn, «Vi brukte badehuset»
    /api/admin/…Innlogginger, økter, regler, unntak og retting

    Feilkoder

    Feil returneres som { "error": KODE, "message": tekst }, og brukeren ser alltid en forståelig norsk melding. De vanligste: SLOT_TAKEN (perioden er tatt), STARTED (har startet – bruk «Sjekk inn nå»), FULLDAY_STARTED (heldag etter kl. 10), OUTSIDE_WINDOW (over 3 måneder), QUOTA_WEEKDAY og WEEKEND_LIMIT (sommerreglene), RATE_LIMITED (for mange feil passord) og RULES_INVALID (feil i rules.json).

    4 Drift og oppsett

    For Thomas, steg for steg i Cloudflare-dashbordet. Alt er på gratisplanene.

    Oppsett i Cloudflare

    Allerede gjort: ht14.no er lagt til som sone på Cloudflare-kontoen, databasen D1 «ht14» er laget og står i wrangler.jsonc, og repoene FluxReveal/ht14 og FluxReveal/ht14-data finnes.

    1. Vent til ht14.no er aktivVelg ht14.no i dashbordet og sjekk at statusen er Active (Cloudflare sender også e-post). Først da kan domenet kobles til Workeren.
    2. Koble repoet (Workers Builds)Workers & Pages → Create application → GitHub. Godkjenn Cloudflare-appen for FluxReveal (gjerne bare repoet ht14), velg FluxReveal/ht14, la byggkommandoen stå tom og velg Save and Deploy. Workeren må hete ht14, som i wrangler.jsonc.
    3. Forhåndsvisning av grenerWorkeren → Settings → Builds: sjekk at produksjonsgrenen er main og at bygg for andre grener (preview builds) er slått på. Lenken for hver gren står under Previews og som kommentar i GitHub.
    4. ht14.no som eget domeneStår allerede i wrangler.jsonc og kobles på ved første publisering. Sjekk under Settings → Domains & Routes (i nyere dashbord fanen Domains). Mangler det: Add → Custom Domain → ht14.no.
    5. HemmeligheterNår innloggingen kommer: Settings → Variables and Secrets → Add, type Secret: SESSION_PEPPER (lang tilfeldig tekst) og GH_DATA_TOKEN (fine-grained token, bare ht14-data, Contents: Read and write, utløp om ca. ett år). Velg Deploy.
    6. Nattlig kopiSenere: fjern kommentaren rundt triggers i wrangler.jsonc og flett inn i main. Cron Triggers styres fra den fila; sjekk under Settings → Triggers.
    7. Test på iPhoneÅpne ht14.no, Badehusappen og ht14.no/api/helse (skal vise {"ok":true}), og legg appen på Hjem-skjermen.

    Innlogginger

    • Nytt hus-passord: administratoren setter det og gir det muntlig eller på lapp. Alle økter for huset avsluttes.
    • Mistet mobil: «Logg ut alle» for huset, og bytt passord.
    • Flytter noen: bytt e-post og passord for huset. Historikken beholdes.

    Endre regler og gjøre unntak

    Når sameiet har bestemt en endring, legges den inn i rules.json som en vanlig endring (se Slik gjøres endringer). Unntak og retting av historikk krever alltid en kommentar og vises i historikken.

    Sikkerhetskopi

    Hver natt skrives bookinger og brukere til ht14-data som CSV (semikolon, UTF-8, åpnes i Excel) og JSON – aldri passord-hasher. Git-historikken viser alle tidligere versjoner. D1 kan i tillegg spoles tilbake inntil 7 dager (Time Travel).

    Når noe feiler

    SymptomHva du gjør
    Siden virker ikke etter en endringRull tilbake: Workeren → Deployments → ⋯ ved forrige versjon → Rollback.
    Endringen kom aldri utSe byggeloggen under Deployments → View build history.
    Kopien i ht14-data oppdateres ikkeSjekk at GH_DATA_TOKEN ikke er utløpt. Beboerne merker ingenting.
    Alle bookinger avvises (RULES_INVALID)Rull tilbake, eller rett rules.json.

    5 Drift og overlevering

    HT14 er en egen pakke som kan overleveres til sameiet. FluxReveal (Thomas) er IT-avdeling og driftsleverandør.

    Hvem eier hva

    • Sameiet eier domenet ht14.no, dataene (bookinger og innlogginger), innholdet og reglene.
    • FluxReveal gjør drift (følger med på at alt virker), sikkerhetskopi (den nattlige kopien) og oppdateringer (endringer, sikkerhet og fornying av token).
    • Begge repoene ligger hos FluxReveal på GitHub og kan overføres til sameiet.

    Slik gjøres endringer

    1. Thomas ber om endringen i chat.
    2. Endringen lages på en egen gren i ht14.
    3. Cloudflare lager en forhåndsvisningslenke, og Thomas tester på iPhone.
    4. Thomas sier «kjør», og grenen flettes inn i main.
    5. Workers Builds publiserer automatisk på ht14.no.
    6. Det kommer en linje i Hva er nytt.
    7. Går noe galt: ett klikk tilbake i Cloudflare (Rollback).

    Slik tar sameiet over

    1. Overfør de to repoene (ht14 og ht14-data) til sameiets GitHub-konto (repoets Settings → Transfer ownership).
    2. Lag sameiets egen Cloudflare-konto (gratis), lag en ny D1-database, legg inn siste kopi fra ht14-data og koble repoet med Workers Builds.
    3. Legg inn hemmelighetene på nytt (ny pepper og nytt token). Da logger alle husene inn én gang til.
    4. Flytt domenet: eierskifte for ht14.no hos Domeneshop til sameiet, og legg ht14.no til i sameiets Cloudflare-konto.
